# ADR 0005: 監査ログ (Audit Logging) の出力戦略と PII 保護方針

## 1. 背景と目的 (Context)
本番環境での運用を見据え、システムへのアクセス監査を行うためのログ出力要件を整理する必要が生じた。
特に「誰が（どのユーザーが）アクセスしたか」を特定するための情報を残す必要があるが、個人情報（PII: Personally Identifiable Information）であるメールアドレスなどはログに出力せず、安全な識別子のみを記録する設計が求められる。

## 2. 決定事項 (Decision)
ユーザーを特定するための識別子として、Cognito が発行する UUID である **`sub` (Subject)** のみを使用し、各レイヤーでのログ出力において `email` 等の PII は一切出力しない方針とする。
また、各コンポーネントにおけるログ出力の可否と実装方針を以下の通り定める。

### 2.1 監査ログとして実現「できること」

- **API Gateway (HTTP API) のアクセスログ**
  - **実現方針**: JWT Authorizer がパース・検証したトークンのクレームから `sub` を抽出し、アクセスログとして CloudWatch Logs に出力する (`$context.authorizer.claims.sub`)。
  - **効果**: 全てのリクエストに対して、どの API パスに、誰が、いつアクセスしたかの証跡をセキュアに残すことができる。
- **Backend (FastAPI / Lambda) のアプリケーションログ**
  - **実現方針**: API Gateway を通過してきた Authorization ヘッダーの JWT (署名検証済み) を Base64 デコードし、`sub` のみを抽出してアプリケーションの構造化ログ (INFO等) として出力する。
  - **効果**: ビジネスロジックのどの処理を誰が実行したかを監査できる。
- **Cognito Authorizer の認可エラーログ**
  - **実現方針**: HTTP API のアクセスログフォーマットに `$context.authorizer.error` などの変数を追加することで、認可に失敗した場合（トークン期限切れ、無効な署名等）のエラー詳細を記録する。

### 2.2 監査ログとして実現「できないこと / すべきでないこと」

- **AWS WAF におけるユーザー識別 (`sub`) の記録**
  - **理由**: WAF は JWT をパースする機能を持たない。WAF ログにユーザー情報を残そうとすると `Authorization` ヘッダー (トークン自体) を丸ごと記録するしかなく、これは致命的な情報漏洩リスクとなるため**厳禁**とする。
  - **代替案**: WAF は IP アドレスや URI、User-Agent 等での追跡に留め、必要に応じてタイムスタンプと IP を元に API Gateway のアクセスログと突き合わせる。
- **Frontend (CloudFront / SPA) におけるインフラレベルのユーザー識別**
  - **理由**: CloudFront などのアクセスログも標準では JWT をパースできない。
  - **代替案**: クライアント側での操作（ボタンクリック等）の監査が必要な場合は、インフラのログではなく、フロントエンドアプリ内に Datadog RUM や Amplify Analytics を組み込み、初期化時にトラッキング ID として `sub` をセットする手法を採用する。

## 3. 結果 (Consequences)
- API 呼び出しにおけるセキュアな監査証跡 (Audit Trail) が確立される。
- 個人情報保護（PII 漏洩防止）と、セキュリティ基準（トークンをログに残さない）を両立できる。
